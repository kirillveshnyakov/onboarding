# Что реализовано мной

## 1. Архитектура backend и OpenAPI-first подход

Я разработал общую структуру backend и границы модулей:

```text
backend/internal/
├── project/
├── scenario/
├── runtime/
├── tracking/
├── analytics/
├── pdf_report/
├── platform/
└── app/
```

Также я продумал общение между модулями и для взаимодействия admin, SDK и backend я зафиксировал API-контракт, написанный в openapi, после чего разные части команды могли разрабатываться параллельно, ориентируясь на одну спецификацию.

API разделен на две основные группы:

```text
/api/v1/*
→ административный API
→ Project / Scenario / Analytics / PDF
→ защищен admin token

/api/v1/sdk/*
→ API для встроенного SDK
→ Runtime / Tracking
→ использует X-Project-Key и optional test token
```

## 2. Модуль Project

Модуль отвечает за управление подключенными к платформе продуктами и их UI-элементами.

Чтобы наш проект не был связанным с конкретным сайтом и позволял создавать онбоардинги для любых продуктов мы выделили сущность `project`, которая идентифицируется токеном project_key. 

При создании проекта backend самостоятельно генерирует `project_key` — публичный интеграционный идентификатор, по которому SDK связывает запрос с конкретным проектом.

Ключ генерируется через `crypto/rand` из 32 случайных байт и кодируется в URL-safe Base64. Уникальность дополнительно гарантируется базой данных. В usecase реализована повторная генерация ключа при крайне маловероятной коллизии.

Различные UI-элементы мы выделили как отдельную сущность `element` и привязали их к проектам. Они нужны для создания сценариев онбординга. 

Реализованые операции управления `project`:

- создание проекта;
- получение проекта вместе с его элементами;
- список проектов с пагинацией;
- изменение проекта;
- soft delete проекта.

Реализованые операции управления `element`:

- создание элемента;
- получение списка элементов проекта;
- частичное обновление;
- soft delete;

Отдельно реализована защита целостности данных: Element нельзя удалить, если на него ссылается существующий Step сценария.

Для предотвращения race condition при таких операциях используются транзакции и блокировки активных записей.

## 3. Модуль Scenario

Модуль отвечает за жизненный цикл онбордингов и их шагов.

Онбординги были выделены в сущность `scenario`. Они состоят из набора шагов, которые выделены в сущность `step`. Шаги привязаны к конкретной странице. Также сценарий хранит страницу триггер, с которой начианется онбординг.

Реализованые операции управления `scenario`:

- создание сценария;
- получение сценария вместе со Steps;
- список с фильтрацией по статусу и пагинацией;
- изменение сценария;
- soft delete;
- publish / enable / disable
- Получение токена тестирования сценария (подробнее ниже)

Реализованые операции управления `step`:

- создание;
- изменение;
- удаление;
- изменение порядка шагов (`reorder`) в сценарии;

Изменения Steps также запрещены для опубликованных активных сценариев.

Критические составные операции выполняются транзакционно с блокировками Scenario / Element / Step, чтобы не допускать конфликтующих изменений.

## 4. Test Token

Для проверки онбординга до публикации реализован тестовый режим.

Я реализовал платформенный сервис генерации и хеширования test token.

В базе хранится не исходный token, а его SHA-256 hash.

Test token ограничен по времени; в текущей конфигурации TTL составляет **30 минут**.

Это позволяет администратору проверить еще не опубликованный сценарий на тестовом сайте, не делая его доступным обычным пользователям и не получая на него лишнюю аналитику.

## 5. Platform layer

Помимо бизнес-модулей я реализовал общие инфраструктурные компоненты backend.

### HTTP server и Router

HTTP-слой построен на стандартном `net/http`.

Реализованы:

- общий HTTP server;
- router поверх `http.ServeMux`;
- регистрация модулей через `RouteRegistrar`;
- route groups, с возможностью добавлять middleware handler к группе запросов, например запросы к админке покрываются проверкой admin_token;
- единый формат JSON-ошибок;
- общие функции для парсинга данных запроса;

Такой подход позволил сделать более структурным подключение бизнес-модулей к серверу.

### Transaction Manager

Для составных операций реализован общий `Transactor` поверх `pgx`:

```go
WithTx(ctx, func(ctx context.Context) error)
```

Транзактор используется в слоях repository и usecase для составления транзакционных запросов в БД.

Текущая транзакция прокидывается через `context.Context`, поэтому repository внутри одного usecase могут использовать один `pgx.Tx` без передачи транзакции через все сигнатуры методов.

## 7. Интеграция приложения

В `internal/app/app.go` я написал сборку backend в единое приложение:

```text
Config
  ↓
PostgreSQL pool
  ↓
Goose migrations
  ↓
Repositories
  ↓
Usecases / Services
  ↓
HTTP handlers
  ↓
Middleware + Router
  ↓
HTTP Server
```

Также реализован корректный lifecycle приложения:

- обработка `SIGINT` / `SIGTERM`;
- запуск HTTP-сервера;
- graceful shutdown с timeout;
- закрытие PostgreSQL pool;
- логирование этапов запуска и остановки.

# Архитектурные решения

### Modular Monolith

Для MVP был выбран модульный монолит.

Причины:

- минимальная операционная сложность во время хакатона;
- один deploy;
- одна база данных;
- простые локальный запуск и отладка;
- при этом бизнес-модули остаются разделены архитектурными границами.

### Clean architecture

Для реализации своих модулей `Project` и `Scenario` была выбрана чистая архитектура.

Причина: 
- Модули являются достаточно большими, чтобы сделать их части более изалированными и избавиться от зависимостей, а также сделать код более структурным и строгим использовалась чистая архитектура с инъекцией зависимостей через интерфейсы.


### OpenAPI-first

`backend/openapi.yaml` использовался как единый контракт между backend, frontend и SDK.

### Soft Delete

Основные конфигурационные сущности не удаляются физически. Это позволяет сохранять связи с историческими данными и не ломать аналитику.

### Транзакции и блокировки

Операции, изменяющие несколько связанных сущностей, выполняются атомарно. Для конкурентно-чувствительных операций используются PostgreSQL row locks.
